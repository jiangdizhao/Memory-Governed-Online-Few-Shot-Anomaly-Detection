# Ledger and deterministic recovery contract

`fs4_durable_ledger.py` creates a non-overwriting run directory and a canonical JSONL SHA-256 chain. Records follow prediction, query, optional label intent and feedback, state transition, and event completion. Each append flushes and fsyncs before returning; the writer lock excludes another process and an I/O failure poisons the writer. A malformed or partial tail is rejected. The ledger checks prediction positions and identities, recomputes the query utility and adaptive price from sealed inputs, verifies the slot/action hash and two-stage probability, and forbids unqueried or duplicate disclosure.

The run manifest must list the full required native and FS4 source fingerprints, committed source identity, frozen scientific contract, model and dataset identity hashes, four Support group identities and fixed-bank digest for each category, query seed, category counts, profile, and registered label-blind event-stream digests. A category Stage A seal requires its registered event sequence and complete five-view groups. The global Stage A seal requires all registered categories. Stage B requires a separate run- and seal-bound authorization and an external verifier; no Stage B evaluator or scientific launch is provided here. A hash chain detects accidental corruption but is not a signature against someone able to rewrite the entire run and its manifest; restrict run-directory access in the eventual deployment.

`fs4_checkpoint.py` serializes named JSON fields and NPZ tensors rather than a pickled object graph. It stores policy histories and receipts, L/E evidence and thresholds, FP32 E feature records, Greedy tensors and source unions, C1 tensors and source unions, Coverage Memory, the immutable Support digest, learning reference, writer counters, source/manifest identity and ledger position. Restore binds evidence to the newly restored policy receipts, checks feature and native state digests, validates C1 provenance, and verifies the ledger prefix.

`begin_recovery` replays already sealed predictions, queries, and legally recorded feedback from the last complete checkpoint. It rejects mismatched event inputs, scorer state or post-state receipts, and never calls the label reader again for a recorded feedback value. A durable label intent with no durable feedback value is ambiguous and fails closed. CPU tests inject failures after prediction, query, feedback, native C1 and Greedy writes, E refresh, and completed state transition; a further test fails midway through twelve native E rescores.

Important review limitation: the manifest records Support, model and dataset identities, but the generic `DurableExecutor` does not independently bind caller-supplied event features or the caller's runtime instance to those registered identities. The Support-only preflight verifies its own four-Support construction separately. A production dataset/encoder adapter with an independently enforced identity binding remains necessary before a scientific campaign. A deployment must also supply and independently validate the Stage B authorization verifier and directory access controls.

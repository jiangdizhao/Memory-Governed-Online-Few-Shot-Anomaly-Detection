# FS4 R2 Stage B and filesystem controls

The production Stage B grant and result receipt use distinct, domain-separated Ed25519 authorities. The grant binds run, protocol, frozen source, dataset and stream manifests, global Stage A seal, evaluation scope, Stage B principal and projection destination. Completion requires a separately signed receipt, verified result bytes and checksum, and a Stage B seal before the overall completion seal. Stage B projection access uses a separate Windows principal and a protected location outside the Stage A run directory. Production does not accept a caller-supplied approval callback.

Synthetic tests exercise the signed authorization and result checks, denial of authorization by an arbitrary callback, denial of completion without a result, and detection of modified result bytes. The production authority file `C:\ProgramData\FS4\trust\authorities.json` was not provisioned during R2; protected production keys, signed run authorizations, and an independently provisioned Stage B account remain prerequisites. Positive end-to-end operation across two real Windows accounts was not tested. No Stage B evaluation or access to scientific outcomes occurred.

The Windows private store establishes and validates protected ACLs for feedback, model and Support provenance, E feature caches, checkpoints, and Stage B projections. Synthetic tests include an actual Windows Authz access check denying an untrusted World SID and rejection of a weakened ACL. These checks and hash chains provide operational isolation and integrity checks; they do not provide cryptographic protection against a full local administrator. Nor do they isolate arbitrary code already executing inside the privileged Python process.

# Data roles and label firewall

The campaign population is exactly the four development categories in `CAMPAIGN_SPEC.json`: 15,295 image events in 3,059 five-view Source Groups. This is not independent external validation.

The future trusted preparation process verifies the original registration and source-group/view identities, reconstructs R7's category-local seed-0 group shuffle, and creates one random opaque mapping and one metadata-free lossless RGB PNG per event. It verifies decoded pixel equality and seals the single registration before any trajectory starts. The same registration, event IDs, group IDs, view order and image resources are used by S, CL and CE.

Stage A receives only the public opaque registration, the metadata-free image resources, model/configuration identity, and the four registered TRAIN-normal Support paths needed for native bootstrap. Stage A never receives original TEST filenames, defect codes, full labels, masks, private mapping, unqueried outcomes, future items or class counts. Full labels remain in a separately protected mapping. A spawned query-only broker gets the private mapping and one trajectory's durable ledger. Each branch has a different disclosure directory. The broker releases one label only after it independently verifies that branch's sealed prediction, executed query receipt and durable label intent. Querying an event in another branch confers no disclosure.

The CPU Stage B process first verifies every one of the twelve mandatory category/trajectory ledgers and seals, their event counts, shared registration, Support/model identities, query receipts and pre-event prediction records. Only then does a separate mapping-verification process project all labels. No masks are projected. This same-account architecture is for a trusted local researcher and is not a malicious-user sandbox.

Real preparation and all scientific execution are disabled by this freeze-only assignment. They require separate campaign-bound authorizations.
